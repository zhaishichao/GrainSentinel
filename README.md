# 🌾 粮情哨兵智能体 · Grain Sentinel Agent

一个面向「粮食安全、粮情实时监测、仓储数据问答」的**多智能体问答/分析系统**。基于轻量自研的
**Supervisor + 子智能体（subAgent）** 架构，围绕我国粮食仓储与质量安全现状，帮助用户完成
粮情监测、质量检测、虫霉防治、智能仓储、储备轮换与安全预警等任务。

前端为 DeepSeek / ChatGPT 风格的网页界面，支持真流式输出与「思考过程」工具轨迹展示。

---

## 1. 项目背景：为什么要做这件事

粮食安全是「国之大者」。我国粮食产量已连续多年稳定在 1.3 万亿斤以上，储备粮规模居世界前列，
但在「收、储、运、加」各环节仍存在一系列真实而紧迫的问题：

- **产后损耗偏高**：我国粮食产后损失率较高，其中储藏环节损耗约 2%~3%，每年损耗量巨大；
- **粮情监测依赖人工**：粮温、水分、虫霉等粮情测控点多面广，传统巡检费时费力、响应滞后；
- **储粮安全风险多**：发热、结露、霉变、虫害是储粮四大风险，一旦失守会造成整仓粮食降等报废；
- **质量安全门槛高**：真菌毒素（黄曲霉毒素 B1、呕吐毒素、玉米赤霉烯酮）、重金属、农药残留等
  检测指标专业性强，判定标准繁多；
- **仓储管控不智能**：智能通风、充氮气调、谷物冷却等「科技储粮」技术落地不足，缺少统一决策支撑；
- **储备轮换靠经验**：宜存 / 不宜存判定、轮换计划制定依赖老师傅经验，缺少量化依据。

这些问题的共同特点是：**数据分散、专业性强、需要跨领域协同决策**。而「大模型 + 多智能体」恰好
适合这种「理解意图 → 调用专业工具 → 协同分析 → 给出可执行结论」的场景。

本项目正是为此构建的一个可运行、可扩展的演示级框架：用多个**专职子智能体**各司其职，由
**主控智能体**统一调度与汇总，把「粮食安全守护」这一复杂任务拆解为可协作的智能体工作流。

## 3. 系统架构

```
用户提问
   │
   ▼
┌─────────────────────────────────────────────────────────┐
│  主控智能体 Supervisor（supervisor）                      │
│  理解意图 → 路由/委派 → 汇总多智能体结论 → 流式输出       │
└───────────────┬─────────────────────────────────────────┘
                │  子智能体即工具（层级委派，subAgent 模式）
   ┌────────────┼────────────┬────────────┬────────────────┐
   ▼            ▼            ▼            ▼                ▼
粮情监测    质量检测    虫霉防治    智能仓储    储备轮换    安全预警
智能体      智能体      智能体      智能体      智能体      智能体
   │            │            │            │            │            │
   └────────────┴────────────┴───── ReAct 工具循环 ───────┴────────────┘
                                        │
                             领域工具（mock 数据，可替换真实接口）
                 粮情测控 / 质量检测 / 虫霉监测 / 仓储管控 / 轮换 / 风险评估
```

**关键设计（体现现代 subAgent 技术）：**

1. **子智能体即工具**：每个子智能体被封装成主控可调用的「工具」（`ask_xxx`），实现层级委派；
2. **统一 ReAct 循环**：每个智能体在「系统提示词 + 专属工具集」下循环执行
   `思考 → 调工具 → 观察 → 再思考`，最多 N 轮；
3. **两阶段输出**：工具循环阶段非流式（稳定），最终回答阶段真流式（体验好）；
4. **结构化 JSON 决策**：LLM 通过 `{"action":"tool",...}` / `{"action":"finish",...}` 决策，
   不依赖模型原生 function-calling，兼容任意 OpenAI 兼容模型。

## 4. 技术栈

| 技术 | 为什么用 | 解决了什么问题 |
|------|---------|---------------|
| **Python + FastAPI** | 轻量、异步、原生支持 SSE 流式 | 用极少代码承载流式问答接口与静态前端 |
| **`openai` SDK（OpenAI 兼容协议）** | 一套代码对接 DeepSeek / 通义 / GLM / OpenAI | 模型可插拔、不锁定厂商，换 Key 即可切换 |
| **自研轻量多智能体框架**（约 200 行） | 无重依赖、逻辑透明、可离线用 stub 调试 | 避免 LangChain/LangGraph 版本兼容坑，清晰呈现子智能体架构 |
| **原生 HTML/CSS/JS + ECharts** | 无构建步骤、可控性强 | 做出 DeepSeek 级界面 + 粮情监测可视化面板 |
| **`python-dotenv`** | 极轻量 | 便捷管理 API Key，避免硬编码 |

## 7. 快速开始

### 7.1 环境要求

- Python 3.8+（开发环境为 3.9）
- 一个 OpenAI 兼容大模型的 API Key（DeepSeek / 通义千问 / GLM / OpenAI 均可）

### 7.2 安装依赖

```bash
cd GrainSentinel
pip install -r requirements.txt
```

### 7.3 配置 API Key

```bash
cp .env.example .env   # Windows: copy .env.example .env
```

编辑 `.env`，填入你的 Key。默认使用 DeepSeek：

```ini
LLM_API_KEY=sk-你的Key
LLM_BASE_URL=https://api.deepseek.com
LLM_MODEL=deepseek-chat
```

### 7.4 启动

```bash
python app.py
```

浏览器打开 **http://localhost:8000**。

### 7.5 运行测试（无需 Key）

```bash
python tests/test_agent.py
```

### 7.6 示例问题


## 8. 多智能体工作流示例

以「评估储备库 C 的粮情安全风险」为例，完整链路：

1. **主控 Supervisor** 理解意图，判定属于安全预警场景，委派给 `warning_agent`；
2. **安全预警智能体** 调用 `assess_risk`（综合风险评分）→ 必要时再调
   `get_grain_condition`（粮情数据）、`get_pest_monitor`（虫霉数据）；
3. 数据齐备后，安全预警智能体**流式生成**风险评分、风险等级与分级处置预案；
4. 主控智能体**汇总并流式输出**最终答案，前端同步展示「思考过程」轨迹与逐字回答。

前端「思考过程」面板会实时显示每一步：`🤖 安全预警智能体` → `🔧 调用工具 assess_risk(warehouse=储备库C) ✓` 等。

## 9. 数据说明

`data/mock_data.py` 中的粮温/水分/仓湿、粮堆气体、真菌毒素与重金属限量、品质指标、虫害密度等
均为贴近我国粮食仓储与质量安全现状的模拟数据（如安全水分：小麦≤12.5%、稻谷≤14.5%、玉米≤14%；
黄曲霉毒素 B1 限量 20 μg/kg（GB 2761）；储粮损耗从传统 2%~3% 降至 1% 以下等）。所有领域工具均为
**纯函数**，后续只需替换函数内部实现为真实数据源（粮库智能化改造平台 / 粮情测控传感器网关 /
检测实验室 LIMS），**无需改动 Agent 框架与前端**。

## 11. 常见问题（FAQ）

**Q1：没有 API Key 能跑吗？** 框架与前端、测试都能跑（`python tests/test_agent.py`），但
问答需要真实大模型，须在 `.env` 配置 Key。

**Q2：为什么换模型只需改配置？** 因为全部通过 OpenAI 兼容协议调用，`LLM_BASE_URL` /
`LLM_MODEL` 决定用哪家模型。

**Q3：流式为什么用两阶段？** 带工具调用的复杂链路下，先非流式收集数据更稳定，最后一段
纯文本再真流式，兼顾可靠性与体验。
